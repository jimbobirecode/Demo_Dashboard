# Deployment

The dashboard runs as a **Render Web Service** defined by [`render.yaml`](../render.yaml) (a Render Blueprint). It shares its Postgres database with the core API, whose deployment is described in its own [docs/DEPLOYMENT.md](https://github.com/jimbobirecode/Demo_core_api/blob/main/docs/DEPLOYMENT.md). Render plan, region and instance count in production: **TO CONFIRM (owner)**.

## Render service

| Setting | Value (`render.yaml`) |
|---|---|
| Service | `type: web`, `runtime: node`, name `royal-dornoch-dashboard` (historical name from the Royal Dornoch demo; renaming it in the Blueprint would create a new service) |
| Plan | `free` in the file; production plan **TO CONFIRM (owner)** |
| Node | `NODE_VERSION=22` (matches `.node-version`; `engines` allows 20–24) |
| Build | `npm install --include=dev && npm run build` — `--include=dev` because `NODE_ENV=production` would skip Vite |
| Start | `npm start` → `node server/src/index.js` |
| Health check | `/api/health` (503 when the database is unreachable) |
| Repository / branch, auto-deploy | **TO CONFIRM (owner)** |

Boot sequence (`server/src/index.js`): Sentry (if configured) → **apply pending migrations** (exit 1 on failure, so the deploy fails its health check and Render keeps the previous version) → listen → warn if `BOOKING_LINK_SECRET` is unset in production → hash any plaintext temp passwords → optional seeding (`SEED_ON_START`) → log user/booking counts per club → start the Stripe payment sync.

## Environment variables

Full list with comments: [`.env.example`](../.env.example).

**Required in production**

| Variable | Notes |
|---|---|
| `DATABASE_URL` | Shared Postgres. TLS is enforced for any non-local host (`lib/db-ssl.js`); to verify the server certificate set `PGSSLROOTCERT` to the provider's CA bundle (Supabase publishes one), use `sslmode=verify-full`, or `DATABASE_SSL_VERIFY=true` for a publicly signed certificate. The role needs `CREATE` on schema `public` (see checklist) |
| `JWT_SECRET` | Generated by the Blueprint. Signs staff and portal sessions |
| `BOOKING_LINK_SECRET` | **Identical to the core API's value.** Never generated here (`sync: false`) |
| `APP_URL` | The dashboard's public `https://` origin. Used in every emailed link and trusted by the CSRF origin check. Unset in production ⇒ an error at every boot, emailed links fall back to `https://democlub.teemail.io`, and only the request's own host is trusted |
| `NODE_ENV=production`, `LOG_FORMAT=json` | Set by the Blueprint |

**Usually set**: `BOOKING_REF_PREFIX` — prefix of references the dashboard issues (waitlist conversions, imported rows without one); one of the core API's profile prefixes (`TMG` default, `RDG` for the Royal Dornoch profile).

**Feature switches** (each page reports what is missing): `SENDGRID_API_KEY`, `FROM_EMAIL`, `FROM_NAME`, `REPLY_TO_EMAIL`; SendGrid template ids (`SENDGRID_TEMPLATE_PASSWORD_RESET`, `…_USER_INVITE`, `…_PRE_ARRIVAL`, `…_POST_PLAY`, `…_OPERATOR_STATUS`, `…_OPERATOR_PAYMENT`, optional payment templates); `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `PAYMENT_SYNC_MINUTES`; `VERO_BASE_URL`, `VERO_PARTNER_KEY`, `VERO_PARTNER_SOURCE`, `VERO_SITE`; `SENTRY_DSN`, `SENTRY_ENVIRONMENT`; branding (`CLUB_*`, `VITE_CLUB_*` — the `VITE_` ones are read at **build** time).

**Never set in production**: `TEST_DATABASE_URL`, `SEED_ON_START=force` (rebuilds sample rows), `DATABASE_SSL=disable` (unless the database is on a private network without TLS).

Render sets `PORT` and `RENDER_GIT_COMMIT` (used as the Sentry release).

## First deploy of the migration runner — checklist

The hardening branch replaces the old hand-run `migration_*.sql` files with versioned migrations that run **automatically on boot**. The first deploy applies `0001`–`0007` to the existing production database. `0001`–`0004` reproduce the schema production already has: every statement checks the catalog first (`pg_temp` guard helpers at the top of each file) and does nothing when its column, index, constraint, table or comment already exists. They still take locks and may add what an older install lacks, so:

1. **Back up production.** Take a provider snapshot / on-demand backup and confirm it completed, or `pg_dump --format=custom "$PROD_DATABASE_URL" > teemail-pre-migrations.dump`. Note the time.
2. **Check the database role.** Run as the role in the dashboard's `DATABASE_URL`:

   ```sql
   SELECT current_user;
   SELECT tablename, tableowner FROM pg_tables WHERE schemaname = 'public' ORDER BY 1;
   SELECT has_schema_privilege(current_user, 'public', 'CREATE');
   ```

   The role needs `CREATE` on schema `public` (to create `schema_migrations` and the new `operator_portal_sessions` table) and `SELECT/INSERT/UPDATE/DELETE` on the tables. It does **not** need to own tables whose schema is already complete: plain `ALTER TABLE … IF NOT EXISTS` would demand ownership even as a no-op, so the migrations check first (proved by `migrate.test.js` "a role that owns no table can run them" and by migrating a copy as a non-owner role). It does need ownership of any table the migrations must actually change — `0007` adds `email_messages.message_id` and two indexes, so the role must own `email_messages`, and any column an older install lacks needs ownership of that table. A comment that differs on a table the role does not own is left alone with a warning.
3. **Pre-flight data checks.** Missing CHECK constraints are added `NOT VALID` and then validated; if existing rows break one it stays `NOT VALID` (enforced for every new or updated row, existing rows untouched) with a `WARNING` in the log. A missing unique index that existing duplicates block is skipped with a `WARNING`. Nothing is deleted to make room, and the deploy does not fail. Run these first so there is nothing to follow up (skip a query whose table or column does not exist yet):

   ```sql
   SELECT source, COUNT(*) FROM bookings GROUP BY 1;                    -- only teemail / imported
   SELECT role, COUNT(*) FROM dashboard_users GROUP BY 1;               -- only admin / staff
   SELECT purpose, COUNT(*) FROM password_resets GROUP BY 1;            -- only reset / invite
   SELECT kind, status, COUNT(*) FROM booking_change_requests GROUP BY 1, 2;
        -- kind: cancel / amend; status: Pending / Approved / Declined / Applied
   SELECT club, LOWER(name), COUNT(*) FROM tour_operators GROUP BY 1, 2 HAVING COUNT(*) > 1;
   SELECT LOWER(email), COUNT(*) FROM dashboard_users WHERE email IS NOT NULL GROUP BY 1 HAVING COUNT(*) > 1;
   SELECT LOWER(username), COUNT(*) FROM dashboard_users GROUP BY 1 HAVING COUNT(*) > 1;
        -- these three must be empty, or the unique index is skipped; resolve by hand,
        -- then add the index in a new migration
   -- After the deploy: any constraint left NOT VALID
   SELECT conrelid::regclass, conname FROM pg_constraint WHERE NOT convalidated;
   SELECT status, COUNT(*) FROM bookings GROUP BY 1;                    -- Pending / Confirmed will be rewritten
   ```

4. **Rehearse on a copy.** Restore the backup into a scratch database and run the dashboard's migrations against it:

   ```bash
   createdb teemail_rehearsal && pg_restore --no-owner --role=<dashboard role> -d teemail_rehearsal teemail-pre-migrations.dump
   pg_dump --schema-only teemail_rehearsal > before.sql
   DATABASE_URL=postgresql://…/teemail_rehearsal npm run migrate
   DATABASE_URL=postgresql://…/teemail_rehearsal npm run migrate:status   # all seven "applied"
   pg_dump --schema-only teemail_rehearsal > after.sql && diff before.sql after.sql
   ```

   Review the diff and any `WARNING` lines. Then point a local core API at the copy and confirm its start-up log has no `❌ DATABASE SCHEMA:` line.
5. **Pick a quiet time.** Each file runs in one transaction with `lock_timeout = 15s`; `0001` takes `ACCESS EXCLUSIVE` locks on `bookings`, `tour_operators`, `waitlist` and `tee_times` for its duration, briefly blocking the core API's writes. A lock that cannot be had within 15 s fails the deploy rather than hanging it.
6. **Deploy the dashboard** and watch the log for `[migrate] applied 0001_… ` … `applied 7 migration(s)` (or `schema up to date`); look for any `WARNING` (a constraint left `NOT VALID`, an index skipped, a comment not set), then `listening on …`. Run `npm run migrate:status` from a shell with the production `DATABASE_URL` if needed.
7. **Then deploy the core API** (see [deploy order](#deploy-order)) and run the post-deploy checks below.

### What 0001–0007 do to an existing database

| File | Effect on a database that already has the tables |
|---|---|
| `0001_baseline_bookings.sql` | Creates `bookings`, `tour_operators`, `waitlist`, `tee_times` only if missing; adds each later column only if missing; sets comments only if missing or different; creates indexes only if missing; adds `bookings_source_check` only if missing (`NOT VALID`, then validated); the unique `idx_tour_operators_club_name` is skipped with a warning if names are duplicated. One-off backfills run **only if their column is being created now**: `pre_play_clock_started_at` = `stripe_paid_at` (or now) for bookings already `Paid`/`Deposit paid`; `waitlist.converted_booking_id/converted_at` recovered from booking notes "Converted from waitlist: WL-…", and those entries set `Converted`. A column that already exists keeps its existing type, default and nullability |
| `0002_baseline_accounts.sql` | `dashboard_users` columns and constraints; **if the `role` column is new, every existing account becomes `admin`** (they could already do everything); if `email` is new, it is copied from usernames that look like addresses; `session_version` added (existing sessions stay valid until their `sv` differs — all current cookies carry none and read as 0); unique indexes on `LOWER(email)`/`LOWER(username)` (duplicates → WARNING, index skipped); `password_resets` with `purpose` |
| `0003_baseline_operator_portal.sql` | Creates `operator_portal_links` if missing (previously created at runtime) |
| `0004_baseline_guest_requests_and_inbox.sql` | `booking_change_requests` and `email_messages` with their CHECKs, `source`/`email_message_id` columns and indexes |
| `0005_retire_legacy_statuses.sql` | `UPDATE bookings SET status = 'Inquiry' WHERE status = 'Pending'`; `'Confirmed'` → `'Booked'` (both services already treated them as equal) |
| `0006_operator_portal_sessions.sql` | **New** table `operator_portal_sessions` (revocable portal sessions) and an index on unused `operator_portal_links` by address. Portal cookies issued before this deploy carry no session id and are refused: operators sign in again |
| `0007_email_messages_message_id.sql` | **New** column `email_messages.message_id`, unique partial index `uq_email_messages_inbound_message_id (club, message_id)` for inbound rows, and `idx_email_messages_pending` for `queued`/`processing` rows (core API de-duplication and recovery). All existing rows have `message_id` NULL, so the unique index cannot meet duplicates |

## Deploy order

The dashboard owns the schema; the core API only checks it.

1. **Dashboard first.** Its migrations run before it listens.
2. **Core API second.** Its start-up log must show no `❌ DATABASE SCHEMA:` line ([core API DEPLOYMENT.md](https://github.com/jimbobirecode/Demo_core_api/blob/main/docs/DEPLOYMENT.md#deploy-order)).

A feature that needs a new column ships as a migration here, deployed first, then the code in either service that uses it. Never the reverse.

## Post-deploy checks

1. `curl https://<dashboard>/api/health` → `{"ok":true,"database":"connected"}`.
2. Log: `schema up to date (7 migration(s))` or the applied list; no `BOOKING_LINK_SECRET is not set` warning and no `APP_URL is not set` error; `dashboard users by club` / `bookings by club` show matching club ids.
3. `curl -i -X POST https://<dashboard>/api/auth/login -H 'content-type: application/json' -d '{}'` → **403** (CSRF header enforced).
4. `curl -sI https://<dashboard>/` shows `content-security-policy` and `strict-transport-security`.
5. Sign in as staff; open a booking; as admin, open **Check payment setup** (`/api/payments/diagnostics`) — every check green.
6. Open a manage-booking link from a recent core API acknowledgement email: it must show the booking (proves `BOOKING_LINK_SECRET` matches).

## Rollback

- Render → service → **Events** → previous deploy → **Rollback**, or redeploy the previous commit.
- **Migrations are forward-only.** Rolling the code back leaves the schema where it is; older code keeps working because migrations only add (the runner warns about versions it has no file for). To undo a migration's effect, write a new migration.
- To return the database itself to a pre-deploy state, restore the backup taken in step 1 ([OPERATIONS.md](OPERATIONS.md#backup-and-restore)) — this loses everything written since, in both services.
- Environment-variable changes are not versioned with the code; record previous values before changing them.

## Secret rotation

Rotation schedule and who may rotate: **TO CONFIRM (owner)**.

### JWT_SECRET

Set a new value (e.g. `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`) and deploy. Every staff and portal session ends; users sign in again. If `BOOKING_LINK_SECRET` is unset, every manage link breaks too — set it first.

### BOOKING_LINK_SECRET

Invalidates **every** outstanding link in both services: `/book` links in availability emails and `/manage-booking` links.

1. Generate a value; set it on **both** the dashboard and the core API; deploy both as close together as possible. Until both are updated, links issued by one fail on the other.
2. Guests with open bookings get a fresh manage link in the next email the dashboard sends about their booking (staff replies from the booking drawer and change-request outcomes include it); otherwise they contact the club.

### SENDGRID_API_KEY

Create a key with Mail Send permission, set it on Render, deploy, send a test (e.g. a password reset), then delete the old key. The core API has its own copy ([core API DEPLOYMENT.md](https://github.com/jimbobirecode/Demo_core_api/blob/main/docs/DEPLOYMENT.md#secret-rotation)).

### STRIPE_SECRET_KEY / STRIPE_WEBHOOK_SECRET

- Secret key: roll it in Stripe (Developers → API keys), set the new value, deploy, check **Check payment setup**, then expire the old key.
- Webhook secret: roll the endpoint's signing secret in Stripe (Stripe can keep the old one valid for a period), set `STRIPE_WEBHOOK_SECRET`, deploy. Deliveries refused in between are retried by Stripe, and the payment sync picks up payments regardless.

### DATABASE_URL password

Shared with the core API: change the password at the provider, update `DATABASE_URL` on both services, deploy both. Until both are updated the stale one cannot connect (`/api/health` → 503).

### VERO_PARTNER_KEY, SENTRY_DSN

Vero: generate a new key, set it in Vero's `PARTNER_INGEST_KEYS` and here, deploy both. Sentry: new client key, update `SENTRY_DSN`, deploy, disable the old key.
